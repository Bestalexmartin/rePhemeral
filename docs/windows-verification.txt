== Before: where the key could be read ==================================

The code as released writes the key with os.open(..., 0o600) and
chmod(0o600). Neither does anything on Windows, and neither raises: the
key keeps its folder's ACL. In the profile that happens to exclude other
standard accounts. In a folder outside the profile, it does not.

$ python -c "config.ensure_key(Path(r'C:\rephemeral-acl-probe\id_ed25519'))"   # released code
$ icacls C:\rephemeral-acl-probe\id_ed25519

discarded:

== Refusing to launder an applied image as stock ======================

StockAlreadyLost fires only when a screen has no stock record and its
current image is one the tool wrote. The tool captures before its first
write, so that state cannot arise honestly on a real tablet. This ran the
real capture against the real tablet over SSH: the device's own sha256,
and is_ours, against a manifest held in memory with poweroff's stock
record absent. Nothing was saved, and the backup directory pointed at a
scratch path.

So the default bind answers IPv4 loopback only, and [::1] is admitted as a
Host once the server listens there. Its startup line printed
http://::1:8766, which is not a URL; it now prints http://[::1]:8766.

In a browser on this machine, typing http://127.0.0.1:8765/ loaded the
app and connected to the tablet. The network panel showed every request
going to 127.0.0.1:8765.

$ rephemeral ui --reload --port 8767        # in the user's PowerShell console
rePhemeral 0.7.0 on http://127.0.0.1:8767
  auto-reload on, watching ~\Projects\rePhemeral\src\rephemeral

The process tree was the venv's rephemeral.exe, the venv python.exe
launcher, the base interpreter as the reload supervisor holding the
socket, and a spawned worker:
  "python.exe" "-c" "from multiprocessing.spawn import spawn_main; spawn_main(parent_pid=22316, ...)" "--multiprocessing-fork"

With web.py's mtime touched, the worker was replaced: 11536 exited and
13296 started. The page still returned 200 and /api/ping reported the
tablet reachable. The plain server on 8765 kept its process and did not
reload.

After Ctrl+C in that console, no process was listening on 8767. The
launcher, the venv python, the supervisor and the worker had all exited,
and no spawn_main process remained.

Started instead with no console (Start-Process -WindowStyle Hidden), the
reloader logged "Reloading..." but the old worker never exited. On Windows
uvicorn restarts a worker by sending it CTRL_C_EVENT, which a process with
no console does not receive. That is a property of that test harness, not
of `rephemeral ui --reload` run from a terminal.
